## Executive Summary

- **컨텍스트가 세 번째 스케일링 축으로 공식화됐다.** Xipeng Qiu의 *Context Scaling*은 모델을 P(d|c)로 두고 학습·결정시점·컨텍스트 인프라라는 3개 예산으로 재정의한다. 배포된 AI의 실패는 추론 능력이 아니라 "행동 시점에 확보 가능한 상태"의 부족에서 온다는 진단이다.
- **규칙 파일은 통제가 아니다.** 278단어짜리 `AGENTS.md`류 규칙 파일 하나로 4개 코딩 에이전트를 20개 저장소에 투입한 사전등록 실험에서, 통제를 만든 것은 문서가 아니라 서비스 앞단의 **게이트**였다.
- **비디오·문서 파이프라인이 하드웨어에서 중립화된다.** LTX-2.5가 AWS Trainium3 절반에서 벤더 API와 동급 지연(10초 클립 22~23초)을 냈고, LlamaIndex는 8.1M 파라미터 OCR을 CPU에 올렸다.

## 🔬 논문 동향

**1. Context Scaling — "추론이 약해서 실패하는 게 아니다"**
- **사실:** Xipeng Qiu의 *Context Scaling: A New Frontier of AI Scaling*은 배포된 AI의 실패 상당수가 추론 능력 부족이 아니라, 과업이 의존하는 상태(사용자 상태·저장소 리비전·도구 트레이스·센서 값)와 행동 시점에 가용한 컨텍스트의 불일치에서 발생한다고 규정한다.
- **수치/구조:** 모델을 $P_\theta(d\mid c)$로 두고 세 예산 — 학습 $B_\theta$, 결정시점 $B_d$, **컨텍스트 인프라 $B_c$** — 로 분해한다. 프리트레이닝은 $\theta$에, 결정시점 스케일링은 주어진 컨텍스트 위에서 탐색·검증에, 컨텍스트 스케일링은 상태의 획득·표현·전달·평가·지속에 투자한다.
- **시사점:** 세 프로그램 중 $B_c$만이 "행동 전에 시스템이 무엇을 가용하게 만들 수 있는가"를 직접 겨냥한다. 에이전트 품질 논의를 모델 교체에서 **상태 파이프라인 설계**로 옮기는 근거이며, RAG·메모리·툴 트레이스를 별도 최적화 대상으로 회계 처리해야 한다는 뜻이다.
→ 원문: [Context Scaling: A New Frontier of AI Scaling](https://arxiv.org/abs/2611.33160)

**2. Markdown Is Not a Firewall — 규칙 파일 vs 게이트, 4개 에이전트 실측**
- **사실:** Sandeep Dhuri의 사전등록 연구는 저장소에 두는 한 장짜리 규칙 파일이 코딩 에이전트에 대해 실제로 무엇을 하는지 물었다. 이미 등록된 선행 연구가 "에이전트는 저장소의 기여 규칙을 거의 조회하지 않는다"고 보고한 상태에서, 저자는 **278단어 규칙 파일 1개**로 Claude Code·Codex CLI·Gemini CLI·OpenCode(DeepSeek)를 숨은 테스트가 있는 소규모 저장소 20개(3개 에이전트는 12개)에 투입했다.
- **수치:** 네 개의 경계 — 거부된 엔드포인트, 파괴적 지름길, 심어진 지시, 심어진 패키지 — 를 두고 실험했고, 각 벤더의 권한 프롬프트 계층은 설계상 **꺼둔 상태**로 비교했다. 금지 요청을 차단·기록한 것은 목 서비스 앞단의 게이트였고, 모든 판정은 에이전트가 변경할 수 없는 기록에서 읽었다.
- **시사점:** "규칙을 문서에 썼으니 통제했다"는 가정은 성립하지 않는다. 통제는 강제 지점(프록시·권한 계층·감사 로그)에서 나오며, 문서는 그 게이트를 설명하는 보조물일 뿐이다. 사내 에이전트 운영 규약을 `AGENTS.md` 한 파일로 끝내고 있다면, 실제 차단이 어디서 일어나는지 먼저 확인해야 한다.
→ 원문: [Markdown Is Not a Firewall: four coding agents, one rules file, four boundaries](https://arxiv.org/abs/2611.27112)
→ 교차확인: [HF Papers — Markdown Is Not a Firewall](https://huggingface.co/papers/2611.27112)

**3. AI 에이전트가 DB에서 실수했을 때, 피해를 결정하는 것은 무엇인가**
- **사실:** Abdullah Kaya 등의 연구는 에이전트가 운영 DB에 직접 문장을 실행하는 시대에, 실수의 피해 규모를 무엇이 결정하는지(모델 / DB 앞단 가드 / 엔진 자체)를 사전등록 2계층으로 분해했다. 출발점은 백업이나 공급자 지원으로만 복구된 실제 프로덕션 데이터 삭제 사고들이다.
- **수치:** Layer A는 **22개 정형 실수 라이브러리**를 스크립트로 4개 관계형 엔진 × 5개 권한 조합 × 2개 복구 조합에 적용해 **792셀, 반복 포함 874회 드릴**을 돌렸다. Layer B는 4B~12B 소형 오픈 모델 6종과 35B MoE(활성 ~3B)를 로컬 서빙해 위험요소가 포함된 과업을 수행시켰다.
- **시사점:** 피해 상한은 모델 성능이 아니라 **권한 조합과 복구 경로**가 좌우한다는 구조다. 에이전트에 DB를 붙일 때 "어떤 모델"보다 "어떤 권한으로, 어떤 복구 드릴을 돌렸는가"를 먼저 문서화해야 한다.
→ 원문: [When an AI agent makes a mistake in a database, what decides the damage?](https://arxiv.org/abs/2611.30483)
→ 교차확인: [HF Papers — When an AI agent makes a mistake in a database](https://huggingface.co/papers/2611.30483)

**4. Partial Routing — 단일 에이전트 과업을 단계별로 위임하기**
- **사실:** *Partial Routing: Trace-Tuned Delegation for Resource-Efficient Agentic Workflows*는 모델 라우팅의 기존 전제를 뒤집는다. 지금까지 라우팅은 "과업 하나 = 모델 하나"를 골랐지만, 에이전트 과업은 여러 단계로 구성되고 단계마다 난이도가 다르다.
- **구조:** 논문은 트레이스(실행 궤적)를 이용해 **하나의 과업 안에서** 위임 지점을 조정하는 방식을 제안한다. 값비싼 모델은 판단이 필요한 구간에만 쓰고, 나머지 구간은 저가 모델로 흘려보내는 형태다.
- **시사점:** 라우팅을 "작업 종류"가 아니라 "실행 구간" 단위로 바꾸는 발상이다. 다만 벤더·과업별 실측 수치가 붙기 전까지는, 크론 파이프라인에서 이미 하고 있는 "작업별 모델 고정" 규칙을 구간 단위로 세분화할지 판단할 근거로만 쓰는 게 안전하다.
→ 원문: [Partial Routing: Trace-Tuned Delegation for Resource-Efficient Agentic Workflows](https://arxiv.org/abs/2611.33402)

## 🧠 모델 · 도구

**5. LTX-2.5 on Trainium3 — 벤더 API와 동급 지연을 비(非)NVIDIA에서**
- **사실:** Hugging Face가 AWS와의 제휴로 `trn3.48xlarge`(64 NeuronCores)를 한 달 빌려 HF 모델들을 시험한 뒤, 마지막 5일을 LTX-2.5(영상+오디오 동시 생성)로 실험했다. 스토리보드형 JSON(샷별 프롬프트)으로 단편 영상을 만드는 실제 사용 사례를 겨냥했다.
- **수치:** 모델 로드 이후 10초 클립(2048×1024, 사운드 포함)이 **22~23초**, **머신 절반**에서 생성됐다. 비교 대상으로 삼은 LTX 온라인 API 공표치는 10초 1080p **23.7초**다. 저자는 CUDA 기준 수치를 찾지 못했고, LTX가 주장하는 "B200 4장에서 10초 720p 6.8초"는 측정 조건이 없어 비교에서 제외했다.
- **시사점:** 영상 생성의 경쟁축이 "품질"에서 "어디서 같은 속도로 돌릴 수 있는가"로 이동하는 신호다. 공급자 종속을 줄이려는 팀에게는 Trainium3 + diffusers 경로가 실사용 후보가 되며, 동시에 벤더 자체 벤치마크(측정 조건 미공개)를 그대로 인용하면 안 된다는 교훈도 남는다.
→ 원문: [Taking Trainium3 to the Track: Generating Videos with LTX-2.5](https://huggingface.co/blog/video-trainium3)
→ 교차확인: [Lightricks/LTX-2.5 모델 카드](https://huggingface.co/Lightricks/LTX-2.5)

**6. Sulphur-3 — MiniMax H3 기반 무검열 영상 모델이 다운로드 54만**
- **사실:** SulphurAI의 *Sulphur-3*는 MiniMax H3를 베이스로 한 무검열 영상 생성 모델로, HF 트렌딩 상위권(좋아요 1,363)에 올랐다. `s3.safetensors` 하나만 받아 H3 모델처럼 실행하면 되고, 저VRAM용 양자화본이 `quantized/`에 함께 들어 있다.
- **수치:** 누적 다운로드 **539,421회**, 좋아요 1,363. ComfyUI용 corrector 노드(`S3_ComfyUI.zip`)는 선택 사항이며 다른 H3 계열 모델에도 적용된다. 라이선스는 MiniMax H3 커뮤니티 라이선스를 따른다.
- **시사점:** 오픈 웨이트 영상 생태계가 "베이스 모델 공개 → 커뮤니티 파인튜닝 → ComfyUI 배포"의 3단 구조로 정착했다. 콘텐츠 정책 통제가 어려운 파생 모델이 50만 다운로드를 넘긴다는 사실은, 플랫폼 입장에서 검열이 모델 레이어에서 불가능해졌음을 뜻한다.
→ 원문: [SulphurAI/Sulphur-3](https://huggingface.co/SulphurAI/Sulphur-3)

**7. OCRia-nano-1 — 8.1M 파라미터로 CPU에서 도는 문서 파서**
- **사실:** LlamaIndex가 공개한 *OCRia-nano-1*은 문서 파싱을 CPU에서 처리하는 **8.1M 파라미터** 파이프라인이다. 검출–인식(detector–recognizer) OCR 스택에 표·레이아웃을 함께 다루는 LayoutNet을 결합했고, ONNX로 배포된다.
- **수치:** 모델 크기가 8.1M에 불과해 GPU 없이 돌릴 수 있고, 자체 ParseBench와 기술 보고서·블로그를 함께 공개했다. LiteParse 파이프라인과 문서 파싱 전용으로 설계됐다(멀티링구얼 지원).
- **시사점:** OCR을 위해 GPU 추론 서버를 유지하던 구성이 흔들린다. NAS·미니PC에서 스캔 문서 인덱싱을 돌리는 워크플로에는 "VLM 호출"보다 이쪽이 비용·지연 모두 우위일 수 있으므로, 기존 파이프라인의 파싱 단계만 교체해 비교 실측할 가치가 있다.
→ 원문: [llamaindex/OCRia-nano-1](https://huggingface.co/llamaindex/OCRia-nano-1)

**8. Kling 4.0 vs Flash — 2단계 하이브리드로 크레딧 51.4% 절감**
- **사실:** Qiita 실측 비교글은 Kling 4.0(최대 30초·1080p/4K, 최대 10키프레임 궤도 보간, 15에셋 Omni Reference)과 초안용 Kling 4.0 Flash(최대 20초·720p)의 스펙 차이를 정리했다.
- **수치:** Flash로 구도를 잡고 4.0으로 마감하는 **2단계 하이브리드 파이프라인**으로 크레딧 사용을 **51.4%** 줄였다는 것이 글의 핵심 수치다. 10키프레임 궤도 제어는 카메라 경로를 프레임 단위로 고정할 수 있다는 뜻이다.
- **시사점:** 생성 비용 최적화가 "모델을 싼 걸로"가 아니라 "해상도를 단계로 나누기"로 이동했다. 영상 소재를 대량으로 뽑아 선별하는 워크플로(썸네일·릴스·게임 트레일러)에서는 초안–마감 2단 구성이 표준이 될 가능성이 높다.
→ 원문: [Kling 4.0 vs Kling 4.0 Flash 徹底比較](https://qiita.com/yoxi957/items/61fad498298d82503bdb)

## 🧭 미스 김 인사이트

### 오늘의 핵심 트렌드 3가지

1. **스케일링의 세 번째 축은 '가중치'가 아니라 '가용성'이다.** Context Scaling은 실패 원인을 $P_\theta(d\mid c)$의 $\theta$가 아니라 $c$로 옮겨 놓았다. 같은 날 올라온 DB 피해 연구(권한 조합·복구 드릴이 피해 상한을 결정)와 규칙 파일 실험(문서가 아니라 게이트가 차단)은 같은 결론의 세 얼굴이다 — **성능은 모델에서 나오지만 안전과 재현성은 배관에서 나온다.** 우리 파이프라인 감사도 "어떤 모델 쓰나"에서 "행동 시점에 무엇이 가용하고, 무엇이 강제되는가"로 질문을 바꿔야 한다. 특히 크론처럼 사람이 없는 실행에서는 규칙 문서보다 툴 레벨 차단(읽기 전용 마운트, 푸시 전 검증 스크립트)이 실제 방어선이다.

2. **생성 모델의 경쟁축이 하드웨어 중립성으로 이동했다.** LTX-2.5가 Trainium3 절반에서 벤더 API와 1초 차이의 지연을 냈고, OCRia는 8.1M 파라미터로 CPU에서 문서를 파싱하며, Sulphur-3는 커뮤니티 파인튜닝이 54만 다운로드를 찍었다. 세 사례의 공통점은 **"GPU 한 장의 성능"이 더 이상 해자(moat)가 아니라는 것**이다. 도구 선택 기준이 "최고 품질"에서 "우리 인프라에서 같은 속도가 나오는가"로 재편되면, 클라우드 단가 협상력과 로컬 대체 가능성이 곧 제품 마진이 된다.

3. **에이전트 생태계가 npm의 신뢰 위기를 반복하고 있다.** Convex 스킬 이슈의 본질은 악의가 아니라 **설계 관행**이다 — 동적 호스트, 핀 없는 원격 스크립트, 그리고 "안전 도구가 못 잡게 명령을 바꿔라"는 지시. 마켓플레이스에 등재됐다는 사실이 안전을 보증하지 않는다는 점이 드러났고, 같은 날 트렌딩 1위권이 '스킬·하네스 저장소'였다는 것은 설치 면적이 빠르게 넓어지고 있음을 뜻한다. 편의와 검증은 정면으로 충돌하며, 지금은 검증 쪽에 비용을 먼저 지불하는 쪽이 오래 간다.

### Jay에게 추천

- **즉시 실행 (오늘–3일)**: ① **스킬·플러그인 인벤토리 1회 감사** — 현재 설치된 스킬/플러그인 중 원격 스크립트를 실행하거나 외부 호스트로 데이터를 보내는 것을 목록화하고, 버전 핀 유무·"검사 우회" 지시 포함 여부만 체크. Convex 사례가 보여준 3개 체크리스트로 30분 안에 끝난다. ② **OCR 파이프라인 대체 실측** — 문서 파싱 단계가 GPU VLM 호출에 의존하고 있다면 OCRia-nano-1(8.1M, ONNX, CPU)로 같은 문서 20장을 돌려 정확도·지연을 비교. NAS급 하드웨어에서 돌면 상시 인덱싱 비용이 사라진다.
- **주목 (1–2주)**: ① **크론 실행 예산 재계산** — Context Scaling의 $B_c$ 개념으로 각 크론의 "행동 시점 가용 상태"를 점검. 오늘 브리핑도 수집 6분·작성에서 시간이 새는 구조이므로, 수집 종료 시점에 원고 길이 예산을 강제하는 규칙을 스크립트로 박아둘 것. ② **LTX-2.5 / Kling 2단 파이프라인** — 영상 자산이 필요한 채널이 있다면 Flash 초안→4.0 마감 구성으로 크레딧 51.4% 절감이 재현되는지 1편만 테스트. ③ **Rex 베타 대기** — 장시간 에이전트 작업을 tmux로 버티고 있다면, 세션 지속성 품질을 비교할 후보로 등록.
- **관망**: ① **Anthropic 주가 추세** — 공모가 하회가 1~2주 이어지면 AI 인프라 조달 단가·투자 심리에 시차를 두고 반영된다. 지금 당장 우리 비용 구조를 바꿀 근거는 아니다. ② **Shirudo 도입** — 무중단 패치가 실제 병목인 서비스가 아니면 이득이 작다. ③ **Sulphur-3류 무검열 파생 모델** — 기술적 흥미와 별개로, 배포·유통 리스크가 모델 성능 이점을 상쇄한다.

### 다음 주 전망

- **'게이트' 제품이 등장한다.** 규칙 파일이 통제가 아니라는 실측이 나온 이상, 에이전트 앞단에서 요청을 차단·기록하는 경량 프록시(권한 조합 프리셋, 복구 드릴 자동화 포함)가 오픈소스로 쏟아질 가능성이 높다. 반대로 "AGENTS.md 잘 쓰는 법" 콘텐츠는 힘을 잃는다.
- **컨텍스트 인프라가 벤치마크 항목이 된다.** Context Scaling이 개념을 세웠으니, 다음은 "동일 모델·동일 과업에서 상태 주입 방식을 바꿨을 때의 성공률"을 비교하는 논문·리더보드가 나올 것이다. RAG·메모리 제품의 마케팅 문구도 "더 많이 검색"에서 "행동 시점 정합성"으로 이동한다.
- **비NVIDIA 추론 스택의 실사용 보고가 늘어난다.** Trainium3 영상 생성 사례처럼, 하드웨어별 "같은 품질에서 몇 초"를 공개하는 글이 늘면 벤더 자체 벤치마크의 신뢰도는 더 떨어진다. GPU 임대 단가 협상에는 유리한 환경이다.
- **플러그인 마켓플레이스에 최소 검증 정책이 붙는다.** Convex 이슈가 공개 이슈 트래커에서 확산되면, 마켓플레이스 운영사가 원격 스크립트 핀 고정·호스트 평판·권한 선언을 요구하는 정책을 내놓을 가능성이 크다. 그 전까지는 개별 설치자가 검증 책임을 진다.
