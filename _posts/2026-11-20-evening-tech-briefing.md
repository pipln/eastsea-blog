## 🛠 개발도구·인프라

### 5. PostgreSQL 19 정식 릴리스 — REPACK CONCURRENTLY, 그리고 플래너에 대한 통제권

PostgreSQL 글로벌 개발 그룹이 19일 [PostgreSQL 19를 정식 릴리스](https://www.postgresql.org/docs/release/19.0/)했다. 가장 실무적인 변화는 `REPACK` 명령으로 디스크 공간 회수와 테이블 재구성을 수행하면서, `CONCURRENTLY` 옵션을 쓰면 읽기·쓰기를 차단하지 않는다는 점이다. 즉 지금까지 pg_repack 같은 외부 확장에 기대야 했던 온라인 블로트 정리가 코어로 들어온다. 여기에 `pg_plan_advice`·`pg_stash_advice`가 추가돼 쿼리 플래너의 결정을 확장 수준에서 저장하고 자동 적용할 수 있게 됐고, 논리 복제는 `wal_level=replica`에서 재시작 없이 활성화되며 시퀀스 값 복제까지 지원한다. 대기 서버에서 자신이 쓴 데이터를 읽는 read-your-writes 일관성(`WAIT` 명령)과 I/O 워커 자동 조절, 병렬 autovacuum도 함께 들어왔다. 운영자 입장에서 이번 릴리스는 '기능 추가'보다 **점검 창을 줄이는 변경**의 묶음이다.

→ 원문: [PostgreSQL 19 릴리스 노트](https://www.postgresql.org/docs/release/19.0/)
→ 교차확인: [Postgres 19 Repack: Faster, Built-In Table Bloat Cleanup (Snowflake Engineering)](https://www.snowflake.com/en/blog/engineering/postgres-19-repack-table-bloat/)

**💋 미스 김의 인사이트**: `REPACK CONCURRENTLY`는 DBA의 야간 작업 목록을 하나 지워주는 변화지만, 동시성 옵션은 그 자체로 추가 I/O와 WAL을 만든다. 업그레이드 전에 반드시 ①가장 큰 3개 테이블에서 소요 시간 ②WAL 증가량 ③복제 지연을 실측하라. 그리고 `pg_plan_advice`는 '플래너를 고정하는 기능'이 아니라 '플랜을 코드로 관리하는 기능'이므로, 적용 이력을 Git에 남기지 않으면 6개월 뒤 아무도 이유를 모르는 쿼리 계획이 남는다.

### 6. FFmpeg 9.1 'Gauss' — 미디어 파이프라인의 조용한 세대 교체

FFmpeg이 [9.1 'Gauss' 릴리스](https://ffmpeg.org/download.html#release_9.1)를 내놓았고, HN에서 160점대 반응을 얻었다. FFmpeg 메이저 버전 변경은 화려한 기사가 되지 않지만, 실제로는 트랜스코딩 팜·스트리밍 서버·NAS 미디어 파이프라인 전체의 기본 동작이 바뀌는 사건이다. 특히 최근 몇 년간 FFmpeg 릴리스는 코덱 추가보다 **API/ABI 정리와 필터 그래프 개선** 쪽 비중이 커졌기 때문에, `libav*`를 직접 링크해 쓰는 자체 빌드 파이프라인이라면 컴파일부터 다시 확인해야 한다. 배포판 패키지가 9.x로 넘어오는 시점에 맞춰, 자체 빌드 스크립트의 configure 옵션과 사용 중단(deprecated) API 목록을 미리 훑어두는 것이 안전하다.

**💋 미스 김의 인사이트**: 우리 NAS 파이프라인처럼 FFmpeg에 의존하는 자동화는 '업그레이드하지 않으면 보안 패치를 못 받고, 하면 인코딩 결과가 미세하게 달라지는' 이중 함정을 안고 있다. 정답은 버전 고정 + 골든 샘플 회귀 테스트다. 짧은 클립 3개(애니·실사·자막 번인)를 두고 해시가 아니라 **SSIM·자막 타이밍**으로 비교하는 스모크 테스트를 먼저 만들어 두면, 9.1 전환은 30분 작업이 된다.

### 7. '이해 가능성을 위한 설계' — LLM이 코드를 늘릴수록 필요한 것은 국소 추론

[LLM 시대의 코드 이해 가능성 설계](https://em-online.bearblog.dev/i-can-tell-you-wrote-this-yourself/)에 대한 글이 HN 200점대에 올랐다. 논지는 명확하다. 모델이 코드를 더 많이 쓰면 개발자의 핵심 책임은 타이핑이 아니라 **품질 판단과 검토**로 이동하는데, 생성된 코드를 이해하지 못하면 LLM은 복잡성을 빠르게 증폭시키는 도구가 된다는 것이다. 제안하는 세 가지 실천은 계약에 의한 설계, 데이터 불변식 명시, 부수 효과와 전역 상태 의존성의 격리다. 공통 원리는 '국소적 추론(local reasoning)' — 현재 코드와 직접 연결된 인터페이스만 읽고도 동작을 예측할 수 있게 만드는 것이다. 이는 곧 리뷰 비용을 낮추는 설계이자, 모델에게 넘길 컨텍스트를 줄이는 설계이기도 하다.

**💋 미스 김의 인사이트**: 에이전트에게 일을 맡길수록 "코드를 예쁘게 쓰기"보다 "한 파일만 읽고 판단할 수 있게 쪼개기"가 생산성을 결정한다. 실무 규칙으로 바꾸면 간단하다. ①전역 상태 신규 도입 금지 ②public 함수에 불변식 주석 필수 ③부수 효과는 경계 한 곳으로. 이 세 개를 CI 린트로 강제하면, 리뷰 시간이 줄고 에이전트의 실패율도 같이 떨어진다.

### 8. OpenSSL CVSS 9.8 버퍼 오버플로(CVE-2026-121481) — Base64 인코딩 경로

OpenSSL에 [EVP_EncodeBlock() 버퍼 오버플로를 수정하는 PR](https://github.com/openssl/openssl/pull/33652)이 공개됐고 CVSS 9.8로 평가됐다. 문제는 Base64 인코딩 결과 길이가 `int` 범위를 넘는 입력을 처리하는 경로에서 발생한다. 수정 과정도 흥미롭다. 처음에는 잘못된 입력에 -1을 반환하는 방식이 검토됐지만, 기존 호출 코드가 반환값을 검사하지 않고 `size_t`로 변환하는 사례가 많아 호환성 문제가 생겼고, 결국 인코딩 함수에 `OPENSSL_assert()`를 넣는 방향으로 바뀌었다. 제안자는 `openssl s_client`에 매우 큰 `-proxy_pass`를 전달하는 명령줄 악용 경로도 확인했다고 밝혔다(명령줄 길이 제한 때문에 비밀번호는 환경변수로 전달해야 했다). 즉 '라이브러리 내부' 문제로 끝나지 않고, 사용자가 직접 실행하는 CLI에서도 재현 가능한 경로가 있다는 뜻이다.

→ 원문: [OpenSSL PR #33652 — Buffer overflow in EVP_EncodeBlock()](https://github.com/openssl/openssl/pull/33652)
